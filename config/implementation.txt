# EPC Gen2 FSM Debug: S_RTCAL→S_DONE Skip Analysis

## Root Cause Investigation

### Question 1: Why does the FSM jump from S_RTCAL straight to S_DONE?

**Answer: This is _correct_ behavior. S_DONE IS the success state of `fs_detector`.**

There is a critical terminology collision in the bug report. The `brain_state` trace from the ILA shows [fs_detector.v](file:///c:/Users/msalam2/EPC-Gen2-Simulation-1-reset/fs_detector.v) states, **not** [cmd_proc.v](file:///c:/Users/msalam2/EPC-Gen2-Simulation-1-reset/cmd_proc.v) states. These are two completely different FSMs:

| `fs_detector` (brain_state) | `cmd_proc` (cmd_state) |
|---|---|
| S_IDLE (0) | Ready (0x0) |
| S_DELIM (1) | Sloting (0x1) |
| S_TARI (2) | Arbitrate (0x2) |
| **S_RTCAL (3)** | **Reply (0x3) ← "PROCESS" in LED mapping** |
| **S_DONE (4)** | Acknowledged (0x4) |
| S_ERROR (5) | SlotTran (0x5) ← "REPLY" in LED mapping |

The `fs_detector` sequence `S_IDLE → S_DELIM → S_TARI → S_RTCAL → S_DONE` means **frame-sync detection succeeded**. There is no "S_PROCESS" or "S_REPLY" inside `fs_detector`—those concepts live in `cmd_proc`.

The S_DONE state in `fs_detector` asserts `sync=1`, which enables downstream `cmd_buf`, `crc5`, and `crc16` to begin capturing the PIE data bits that follow the preamble.

> [!IMPORTANT]
> **The actual bug is that `cmd_state` (from `cmd_proc`) stays at `Ready (4'h0)` — which maps to Solid Blue on LD0.**
> The frame-sync detector works. The command processor never transitions because it never receives a valid decoded command on `clk_cp`.

### Why `cmd_state` stays at Ready (4'h0):

The signal chain after `sync` is asserted:

```
fs_detector.sync → cmd_buf (clocked by clk_dpie) → cmd[7:0] + param[51:0]
                 → cmd_proc (clocked by clk_cp) → ps (present state) = cmd_state
```

`cmd_proc` runs on `clk_cp`, which is generated by [crg.v](file:///c:/Users/msalam2/EPC-Gen2-Simulation-1-reset/crg.v). The `crg` module derives `clk_cp` from the `clk_dpie` signal. In the FPGA hardware mode:

```verilog
// fpga_top.v line 174
.clk_dpie(reader_cmd),     // In FPGA mode, dpie = pie_code
```

Both `pie_code` and `clk_dpie` are wired to `reader_cmd` (= `rfid_in ^ btn2`). This means the CRG is using the **raw RF signal as a clock**. For command processing to work, the CRG must see the full PIE-encoded command data including proper bit transitions — not just the preamble.

**Root cause candidates for `cmd_state` staying at Ready:**
1. The ThingMagic M6e sends a Query command after the frame-sync, but `crg`'s clock generation logic may not produce valid `clk_cp` edges from the over-the-air signal
2. The `cmd_buf` may not successfully decode the Query command bits due to timing mismatches between `clk_dpie` and `pie_code` (they are the same signal in FPGA mode)
3. Even if Query is decoded, with Q=0 the slot calculation forces `slot <= 0` (via `debug_switch=1`), so transition is `Ready → Sloting → Reply` — but only if `cmd_checked == Query` and the inventoried flag matches

### Question 2: RTcal Timing Analysis at 5 MHz / Tari = 6.25 µs

#### EPC Gen2 Specification for RTcal

Per EPC Gen2 §6.3.1.2.3:
- **RTcal** defines the data-0/data-1 boundary (pivot = RTcal/2)
- RTcal must satisfy: **2.5 × Tari ≤ RTcal ≤ 3.0 × Tari**
- At Tari = 6.25 µs: **15.625 µs ≤ RTcal ≤ 18.75 µs**

#### Clock Tick Calculations (5 MHz, 200 ns/tick)

| Symbol | Duration (µs) | Ticks (exact) | Ticks (integer) |
|---|---|---|---|
| Tari | 6.25 | 31.25 | 31 |
| RTcal min (2.5×Tari) | 15.625 | 78.125 | 78 |
| RTcal nom (2.5×Tari) | 15.625 | 78.125 | ~78 |
| RTcal max (3.0×Tari) | 18.75 | 93.75 | 93 |

#### Current [fs_detector.v](file:///c:/Users/msalam2/EPC-Gen2-Simulation-1-reset/fs_detector.v) RTcal Validation Logic

```verilog
// Line 200: S_RTCAL validation
if (pulse_counter > {tari_count[14:0], 1'b0})  // i.e., RTcal > 2 × Tari
```

This checks `RTcal > 2 × Tari`, NOT the spec-mandated `RTcal ≥ 2.5 × Tari`.

With `tari_count = 31` (measured): pivot = `2 × 31 = 62`.
So any `pulse_counter ≥ 63` passes. This is **very permissive** — the spec says 78–93.

#### Noise Margin Analysis

For the RTcal validation to **fail** (→ S_ERROR), the measured RTcal would need to be `≤ 62 ticks` (≤ 12.4 µs). Given:
- Nominal RTcal is ~78 ticks (15.6 µs)
- You'd need **16+ ticks of shortening** (~3.2 µs of noise)

> [!NOTE]
> **The RTcal check is extremely unlikely to fail.** The `> 2×Tari` threshold (62 ticks) has a massive 16-tick margin from the nominal 78-tick RTcal. Analog noise would need to shorten the pulse by >20% to cause a false reject. The current validation is permissive — it's essentially just checking "is this clearly longer than a data-0?"

**Verdict: RTcal validation is NOT the problem.** The FSM correctly passes through S_RTCAL→S_DONE.

### Question 3: Why the Pulse Stretcher Fails to Turn LD0 Red

The pulse stretcher is mapped to the **PROCESS** LED state, which activates when:

```verilog
// fpga_top.v line 308
wire is_process = (active_state == 4'h3) | (active_state == 4'h4);
```

In Smart Mode (`sw_diag_mode=0`):
```verilog
// fpga_top.v line 290
wire [3:0] active_state = sw_mode_sync ? diag_state_mapped : cmd_state;
```

So `is_process` requires `cmd_state == 4'h3` (Reply) or `4'h4` (Acknowledged).

**But `cmd_state` stays at `4'h0` (Ready)**. The `cmd_proc` FSM never transitions because:

1. `fs_detector` asserts `sync` ✓
2. `cmd_buf` needs `sync` + `clk_dpie` edges to shift in command bits
3. In FPGA mode, `clk_dpie = reader_cmd = rfid_in ^ btn2` — the command clock IS the data
4. The `crg` module generates `clk_cp` (the cmd_proc clock) from internal state machines that depend on seeing properly decoded command data
5. If `crg` never generates `clk_cp` rising edges, `cmd_proc` never evaluates its next-state logic

> [!CAUTION]
> **The pulse stretcher works perfectly — it simply never gets triggered.** The `is_process` signal is always 0 because `cmd_state` is stuck at `Ready (4'h0)`. The downstream command processing pipeline (`crg` → `cmd_proc`) is the broken link, not the LED logic.

## Proposed Changes

### Emergency Bypass: Force `fs_detector` into a synthetic "PROCESS" indicator

Since the user wants to verify the LED/pulse-stretcher chain independently of command processing, the cleanest approach is to add an **emergency bypass** in [fs_detector.v](file:///c:/Users/msalam2/EPC-Gen2-Simulation-1-reset/fs_detector.v) that holds in a new state (mapped to trigger the PROCESS LED) for a visible duration after a successful frame-sync.

> [!WARNING]
> This bypass is a **debug-only** modification. It will prevent normal command processing while active because it delays the S_DONE → idle cycle.

#### [MODIFY] [fs_detector.v](file:///c:/Users/msalam2/EPC-Gen2-Simulation-1-reset/fs_detector.v)

Add a compile-time `EMERGENCY_BYPASS` flag. When defined:
- After RTcal validates, instead of going to S_DONE, the FSM enters a new `S_FORCE_PROC` state (value 3'd6)
- `S_FORCE_PROC` holds for ~3.35 seconds (24-bit counter @ 5 MHz) then transitions to S_DONE
- A new output `force_proc` is asserted during `S_FORCE_PROC`

#### [MODIFY] [fpga_top.v](file:///c:/Users/msalam2/EPC-Gen2-Simulation-1-reset/fpga_top.v)

Wire the `force_proc` signal to force `active_state` into `4'h3` (PROCESS), directly triggering the pulse stretcher and Red LED.
